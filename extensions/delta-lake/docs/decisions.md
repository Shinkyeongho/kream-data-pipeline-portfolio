# 구현 판단과 개인 수행 범위

## 기존 프로젝트를 왜 확장했는가?

기존 MySQL 정제 규칙을 Spark로 다시 표현하고 Delta의 저장 버전·MERGE·재시도를 배우기 위한 개인 학습 확장입니다. MySQL이 처리량을 감당하지 못했다거나 Delta로 비용·속도를 개선했다는 비교 근거는 없습니다.

같은 원본·규칙을 기준으로 초기 결과를 만든 후 저장 버전, 배치 반영, Gold 대조를 확인하는 범위로 진행했습니다. 단순 사용 기술 나열보다 무엇을 실행해 확인했는지를 제시합니다.

## 원문과 변환 후보를 분리한 이유

금액 오류를 0으로 바꾸면 정상 0원과 구분할 수 없고 합계·평균의 의미가 달라집니다. 원문을 유지하고 유효 후보를 NULL로 두며 실패 이유를 남겼습니다. 후보 NULL과 원본 행의 격리·제외는 별도 판정입니다. [숫자 후보 코드](../lessons/03_numeric_candidates.py)

허용 형식·단위만 처리합니다. 달러는 고정 1,350원, 시간은 분으로 통일합니다. UTC Z 표기에만 9시간을 더하고 시간대 없는 값은 기존 정책에 따라 KST로 간주합니다. TimestampNTZ는 KST라는 의미를 자체 저장하는 시간대 타입이 아닙니다. [시각 코드](../lessons/04_datetime_candidates.py)

## 형식 검사와 마스터 참조를 분리한 이유

사번이 KRM과 숫자 6자리로 구성됐어도 정상 마스터에 없으면 담당자를 확인할 수 없습니다. 반대로 없다는 이유만으로 가짜 사번이라고 확정하지 않고 원문·참조 실패 사유를 보존합니다. 마스터의 키 유일성을 먼저 확인해 조인 후 행 증가를 막았습니다. [사번 코드](../lessons/05_ids_employee_reference.py)

카테고리 결측은 정상 상품 코드·보정 전 이름 근거·상품별 단일 카테고리 매핑이 있을 때만 복구 후보를 만듭니다. 실제 복구 후보 1,000행 중 정상 마스터 971행·격리 마스터 29행으로 다시 구분했습니다. 복구 성공을 참조 유효성으로 확대하지 않았습니다. [카테고리 결과](../results/lesson-07-latest.json)

## 최신 입력보다 최신 유효 개정을 선택한 이유

같은 ID의 개정 2가 오류이고 개정 1이 정상일 때 개정 번호만으로 2를 선택하면 정상 현재 상태를 잃습니다. 품질을 통과한 개정끼리 최대 REV_NO를 선택합니다. 같은 개정 안에서 원문이 다르면 먼저 격리합니다.

REV_NO와 Delta 버전은 다릅니다. 업무 개정 2인 행도 새 테이블에 처음 쓰면 Delta 버전 0에 있을 수 있습니다. 가상 사례에서 추출 시각과 개정 번호가 역전돼도 유효 개정 번호를 기준으로 선택하는지 확인했습니다. [초기 Silver 코드](../lessons/08_revision_silver.py)

## 원장과 내용 멱등성을 함께 사용한 이유

같은 입력을 재반영해도 업무 값과 행 수를 유지하는 것과, 완료된 배치의 실행 자체를 건너뛰는 것은 다릅니다. 가상 MERGE에서는 내용이 같아도 로그 버전이 증가했고, 완료 원장을 확인해 건너뛴 경로는 대상·원장 버전 모두 유지됐습니다.

데이터 반영 후 완료 기록 전에 중단될 수 있으므로 STARTED를 데이터 미반영의 증거로 사용하지 않습니다. 같은 내용으로 다시 반영하고 완료를 기록하는 경로를 시험했습니다. 단일 실행자와 정제 완료 입력을 전제로 하며 외부 부작용까지 exactly-once라고 부르지 않습니다. [원장 예제](../lessons/10_batch_ledger.py) · [실제 재생](../lessons/11_real_silver_replay.py)

## Gold의 두 분모를 유지한 이유

현재 검수 결과는 ID별 최신 상태를 사용하고, 작업량은 정상 이전 개정도 포함한 유효 개정 대표 전체를 사용합니다. 중복을 제거하되 정상 과거 작업 기록까지 버리지 않는 기존 기준입니다. 거래금액 합계를 매출로, 정책 계산 배상금을 실지급액으로 해석하지 않습니다. [Gold 코드](../lessons/12_gold_daily.py)

## 개발 방식과 수행 범위

기존 팀 프로젝트에서 직접 맡은 업무는 MySQL Bronze → Silver 정제·적재와 Gold 해석을 위한 검증·추론입니다. 나머지 작업은 공동 수행이고 기존 Pandas 분석 코드는 다른 팀원 작성입니다.

개인 Delta Lake 확장에서는 기존 명세·SQL 비교, 구현·검사 코드와 문서 작성에 생성형 AI 지원을 활용했습니다.

직접 수행한 작업은 단계별 로컬 실행, 검사 결과 확인, 정제·개정·참조·집계 기준과 재시도 동작의 학습입니다. 초기 Silver와 배치 재생 결과의 전 컬럼 대조, Gold 집계 대조의 통과 결과를 확인했습니다. 구현 결과와 확인한 범위는 [실행 근거](validation.md)에 연결했습니다.
